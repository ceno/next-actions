# M0a — first live run against Trello, 2026-09-15

**This is the first time anything in this repo has run against Trello.** It is registered, enabled,
and it does not render. What follows is what was established, with the evidence, and what was ruled
out. Nothing here is inferred from documentation.

## Correction to `docs/session-2026-09-15.md` §1b

**That section is wrong and should not be relied on.** It claims the account's boards have no
checklists, based on the MCP GraphQL surface returning `checklists: []` for all 120 cards sampled.

Seen directly in the browser: **nearly every card on "Personal Assistant" carries a checklist**, with
Trello's own native badge showing `☑ 2/5`, `☑ 1/3`, `☑ 6/7`, `☑ 2/3` and so on. One card's checklist
is even named "Next Actions".

The MCP GraphQL surface simply does not populate `checklists` on a card node. I read an empty field
as an empty world. The lesson is the one this project already had written down and which I did not
apply: *`[]` is not the same as "we do not know"* — the very distinction `Unavailable` exists for in
`data.ts`. Checklist fixtures **can** be built from this account; §1b's blocker is void.

## The symptom

**Trello never creates the connector iframe.** Not on board load, not on card open, not when a
capability is invoked by hand.

- `document.querySelectorAll('iframe').length` on the board is **0**, before and after enabling.
- The connector host's access log shows **zero requests from Trello** for `index.html` or any asset,
  across many board loads and hard reloads.
- Clicking **Settings → Edit Power-Up settings** (our `show-settings`) does nothing at all: no popup,
  no request, no error.
- The browser console carries **no Power-Up error of any kind** — only Trello's own React hydration
  warnings from its `ltp.*.js` bundle.

## What was ruled out, and how

Each of these is excluded by direct evidence, not by reasoning.

1. **Our page is broken.** No. Loaded directly, `index.html` serves, `p.trellocdn.com/power-up.min.js`
   loads, `typeof window.TrelloPowerUp === 'object'`, our bundle loads, no console errors.
2. **Wrong CDN domain.** No. The known community failure is the dead `p.trello.com`; we use
   `p.trellocdn.com`, and it resolves and loads.
3. **`X-Frame-Options` / CSP.** No. `curl -I` shows no `X-Frame-Options`. Decisively: an iframe
   pointing at the connector, **injected into the trello.com board page itself**, loaded fine and
   produced the full set of asset requests in the log. Framing the connector from trello.com works.
4. **Extension or DNS blocking of `*.trycloudflare.com`.** No — same injected-iframe result.
5. **Capabilities not declared in the admin UI.** No. `GET /1/plugins/<id>` returns all six.
   (Worth noting: the admin toggles do **not** persist if set by assigning `checkbox.checked`; they
   need a real click that fires the handler. Verified by reload each time.)
6. **Wrong connector URL.** No. The API returns exactly the URL registered.
7. **Not enabled on the board.** No. `GET /1/boards/<id>/plugins` lists it alongside Card Aging,
   Butler and Bulk Actions.
8. **Missing listing.** Ruled out by adding one — name, overview, description. No change.
9. **Stale board/plugin state.** Ruled out by disabling and re-enabling the Power-Up. No change.
10. **Trello cannot reach the host.** No — and this is the sharpest evidence. On saving the icon,
    **Trello fetched `/icon.png` from the tunnel** (logged, `200`). Trello's infrastructure reaches
    our host. Its client still never requests `index.html`.

## What is left

The board is rendered by Trello's **new** client (`ltp.*.js`; the Inbox / Planner / Board / Switch
boards bar). The remaining hypothesis is that this client does not mount custom Power-Up connector
iframes, or does so under a condition not met here. Two observations point that way:

- Opening a card, the card's **Power-Ups menu lists "Card aging" and then one empty grey row** — an
  entry the client is trying to render and cannot. That is almost certainly ours.
- No opt-out back to the classic client was found: Labs offers only "Custom Widget Cards", and the
  account menu has no switch.

This is a **hypothesis, not a finding.** It has not been confirmed, and it was not tested on a second
board or a second account.

## Consequences for the project

- **E1 and E7 did not run.** No `card-badges` callback ever executed, so nothing was learned about
  whether the client library serves `checkItems` (E1) or whether `badges.checkItems` exists (E7). The
  `CONFIG` diagnostic (Path A with Path C behind it) was designed to separate those two by eye and
  never got the chance.
- **E1's cold-board discipline is spent on this board.** A card was opened on "Personal Assistant"
  deliberately, to test whether the connector mounts on card open. Use a different, untouched board
  when E1 can finally run.
- **`CONFIG.dataPath` is left at `'client'`** with `degradeToAggregate: true`. That is the diagnostic
  build, not a decision. It reverts to `'rest'` in one line.

## Next things to try, cheapest first

1. Enable it on a **second board**, and ideally in a **second browser profile**, to separate
   account-wide from board-specific.
2. Ask on the Atlassian developer community whether the new Trello client mounts custom connector
   iframes — the symptom is specific enough to be recognised.
3. Try a **named** tunnel or a static host (GitHub Pages) to remove `trycloudflare.com` from the
   picture entirely. Ruled unlikely by the icon fetch, but it is cheap.
4. Register a second, deliberately trivial Power-Up — one `card-badges` callback returning a single
   hardcoded badge — to prove the platform end to end independently of this codebase.
