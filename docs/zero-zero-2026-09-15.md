# The `0/0` card front, 2026-09-15

> **Partly superseded, 2026-09-15.** This document repeatedly reports that the connector iframe
> "still does not mount in this browser profile", inferred from a silent host access log. That
> inference was wrong: the tab was hidden, and Trello does not issue Power-Up requests for a hidden
> page, so the log could not have shown anything. The `appKey` defect diagnosed at the end was real
> and worth fixing, but it is not what kept the connector from loading. See
> `docs/visibility-2026-09-15.md`.

Reported: the Power-Up "picks up that checklists exist, but it always says `0/0` on the front of the
card."

## What `0/0` can and cannot mean

`0/0` is not a rendering fault. `headerBadge` takes `total` from `checklist.items.length` and nothing
else, so a `0/0` badge means `computeBadges` was handed a checklist with an empty `items` array and
rendered it faithfully. The fault is upstream of the badge logic, in the data path.

Under the diagnostic build (`CONFIG.dataPath: 'client'`, `degradeToAggregate: true`) exactly two
paths can put an empty checklist in front of `computeBadges`:

| Path | Badge text | Requires |
|---|---|---|
| A — `t.card('checklists')` returns stubs | `0/0 <name>` | `checkItems: []` on a real checklist |
| C — `t.card('badges')` aggregate | `0/0` (no name) | `badges.checkItems === 0` |

Path C is ruled out by direct observation: Trello's **native** badges on "Personal Assistant" read
`☑ 2/5`, `☑ 1/2`, `☑ 0/1` — correct, non-zero counts drawn from the very board-level cache that
`badges.checkItems` reads. So the card-level totals are present and are not zero.

That leaves Path A, which is the failure SPEC.md 6.2 predicted all along.

## Why the existing guard did not catch it

`adaptChecklist` already had a guard for this, and its comment names the exact symptom — a stub "must
read as unavailable, never as an empty checklist, which would render a misleading 0/0 badge".

It did not fire, because it tests the wrong thing:

```ts
const rawItems = r['checkItems'] ?? r['items'];
if (!Array.isArray(rawItems)) return null;   // absent -> caught
```

The documented failure does not spell itself as an **absent** `checkItems`. It spells itself as an
**empty** one. A stubbed checklist is well-formed: it has an id, a name, a pos, and `checkItems: []`.
It adapts cleanly, passes every validation we own, and renders a badge that looks like a fact.

Nothing inside the checklist object can distinguish "stub" from "genuinely empty". The distinction
only exists by comparing against something outside it.

## The fix

`clientSource` now fetches `t.card('checklists', 'badges')` — one call, so both views see a single
cache state — and cross-checks its own answer against the card's own total:

```
adapted items < badges.checkItems  ->  unavailable('client cache served N of M check items')
```

Three properties matter, and each has a test:

- **Strictly fewer**, not "different". Equality passes, so a checklist that is *genuinely* empty
  still renders its honest `0/0`. The check catches the lie without outlawing the truth.
- **Absent totals disable the check**, rather than blocking the path. A falsifier that cannot run
  has proved nothing, and must not be read as proof of failure.
- **Partial stubs are caught too** — some items is still not all of them.

`badgeTotals` is now the single reader of those counts; Path C uses it as well.

### What the card shows now

With `degradeToAggregate: true`, a stubbed card no longer renders `0/0`. Path A reports unavailable,
Path C answers from the same counts the native badge uses, and the card front reads **`2/5`** — a
correct, nameless aggregate pill. Degraded, but true. `test/connector.test.ts` asserts the whole
chain end to end, including that `0/0` is not among the badges.

## Status of the underlying experiment

**This is a hypothesis fix, not a confirmed observation.** It is derived from the reported symptom
plus the documented Path A failure mode, and it is consistent with every count seen on the board. The
raw stub payload was **not** observed directly, because the connector iframe still does not mount in
this browser profile — re-verified today: `document.querySelectorAll('iframe').length` is `0` on
"Personal Assistant" after a hard reload, while `GET /1/boards/<id>/plugins` confirms "Next Actions
(dev)" is enabled and the registered tunnel URL serves `200`. The blocker in
`docs/m0a-live-run-2026-09-15.md` is unchanged in this profile.

So E1 has still not been *run*. What has changed is that E1's red outcome is now the working
assumption, and the code no longer renders a falsehood when it holds.

The real repair remains Path B (`CONFIG.dataPath: 'rest'`), which is the only path that yields
per-checklist names and item badges. It needs `CONFIG.restApiKey` and a user authorization; the
real-payload fixture shows the REST shape is exactly what the adapter expects.

## Follow-up, same day: Path B wired

The `2/5` above is Path C, and Path C can only ever be a progress pill — it synthesises one
**nameless** checklist of **nameless** items from the card's count pair. It cannot name a next
action. So the fallback fixed the lie without delivering the product.

Path B is now live:

- A Trello Auth API key was generated for "Next Actions (dev)" and set as `CONFIG.restApiKey`. It is
  public by design and ships in the bundle; the Secret was not read and is not used.
- The tunnel origin was registered under **Allowed origins**, without which Trello refuses the
  authorization redirect.
- `CONFIG.dataPath` is `'rest'`. `degradeToAggregate` stays on, but now sits *below* Path B: a REST
  blip degrades to a true aggregate pill instead of a blank card.

### `showIncompleteItems` now defaults ON

The old default emitted headers only, to avoid duplicating Trello's native card-front checklist
expansion. That reasoning was sound and the conclusion was still wrong: the pills are the thing
Trello **already** does, so the default withheld the only output this Power-Up exists to produce.

### The bare-checkbox trap that came with it

Turning items on by default broke the Path C fallback in a way no existing test caught. Path C's
items have `name: ''`, so `itemBadge` would render `join('☐', '')` — a row of bare `☐` glyphs saying
nothing at all. The fallback now forces `showIncompleteItems` and `showCompletedItems` off for its
own output, whatever the user asked for, because it has no item information to honour.

### Still outstanding: the authorization click

Path B needs a per-member token, obtained once through `t.getRestApi().authorize()`. That click could
not be performed from the automated browser session, because the connector iframe **still** does not
mount there — re-verified after this change: zero iframes on the board after a hard reload.

**Until that click happens, cards show "Connect your account" rather than `2/5`.** That is by design
(`showUnauthorizedBadge`) and is a deliberately louder failure than a blank card, but it does mean
the card front is worse until authorization completes.

## Correction: the connector DOES mount, and what actually broke it

Two claims in the sections above were wrong, and the way they were wrong is worth keeping.

**1. "The connector never mounts."** It mounts. `document.querySelectorAll('iframe').length` is `0` on
the board, but the connector iframe is real — the host access log shows Trello fetching
`index.html` and every asset. Whatever Trello's newer client renders Power-Up iframes into is not
reachable from the page's own DOM. **An iframe count is not a mount check; the server log is.**

What the card fronts showed all along, once actually looked at, was an **orange `2/5` pill sitting
next to Trello's grey native `☑ 2/5`** — our badge, on the Path C fallback, duplicating the native
badge beside it. The earlier `0/0` was the same badge before the stub fix.

**2. "Path B just needs the authorize click."** No. Path B was broken by our own code.

### The `appKey` defect

`t.getRestApi()` throws **synchronously** unless the client library was initialized with an
`appKey`. `initialize()` was passing only `{ localization }`. And the guard that looked like it
covered this:

```ts
await t.getRestApi().isAuthorized().catch(() => false)
```

does nothing, because the throw happens before there is a promise to attach `.catch` to.

That is not a Path B problem. `authorization-status` calls it on **every board load**, so from the
moment Path B shipped, that capability threw every time — and the Power-Up stopped rendering
anything at all. The badges did not degrade; they vanished. The log shows the last connector fetch at
`11:42:40`, the moment the appKey-less Path B build first loaded, and **not one fetch afterwards**
across many reloads, a URL change and a disable/re-enable.

Fixed by passing `appKey`/`appName` to `initialize`, and by routing every `getRestApi()` call through
a `restApi(t)` helper that catches the synchronous throw. `test/connector.test.ts` pins it with a `t`
whose `getRestApi` throws: `cardBadges` must resolve, not reject, and still render `2/5`.

### Two other real bugs found on the way

- **`icon.png` 404.** `publicDir: false` plus `emptyOutDir: true` meant every clean build deleted the
  hand-placed `dist/icon.png`. Trello's `GET /icon.png` 404ed and the Power-Up rendered in Trello's
  menus as a nameless blank row. The vite `staticAssets` plugin now emits it, alongside the locale
  bundles, for the same reason: nothing imports them, so nothing else copies them.
- **The dev server cached the connector.** `python3 -m http.server` sends no `Cache-Control`, so the
  browser heuristically cached `index.html` and Trello kept framing a stale bundle — every rebuild
  appeared to do nothing. Replaced with a small server that sends `no-store` and suppresses
  `Last-Modified` (so conditional GETs cannot 304 back into the stale copy).

### Where it stands

All three fixes are in and the suite is green, but **the fix has not been observed working on the
live board**: Trello has not re-fetched the connector since it broke, so it is still running the
appKey-less bundle from memory. Disabling and re-enabling the Power-Up (with "Keep all Power-Up
data") did not trigger a fetch either.

The safe property is that the worst case is no longer blank. With `degradeToAggregate` on and the
guard in place, a Path B that cannot authorize falls through to the aggregate pill, so the floor is
`2/5` rather than nothing.

Popup surfaces remain unusable on this client regardless: `settings.html` is **fetched** when the
Power-Up's menu entry is clicked, and then nothing paints. That is why the authorize flow could not
be driven from the browser — it needs a popup.
